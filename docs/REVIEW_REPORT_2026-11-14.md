# 2026-11-14 Space Intel 运行诊断与首轮优化

本轮目标是核对 scheduled Worker 错误及其对数据更新的影响，并按用户选择的免费方案准备修复。以下时间均为北京时间；生产观察与本地验证分开记录。

## 生产结论

- 控制台最终复查：过去 24 小时 24 次调用，11 次 CPU 时间超限，错误率 45.8%；未捕获异常、内存超限均为 0。生产仍为旧部署版本。
- 账号使用 Workers Free。Cloudflare 当前文档列出的免费 CPU 预算为每次 Cron 调用 10ms；外部子请求上限为 50。代码此前在同一次调用内执行全部 60 个启用来源，串行/有界并发不会重置调用预算。
- D1 原始日志确认后半段官网/采购来源反复报 `Too many subrequests by single Worker invocation`。这与被捕获的上游 HTTP 失败不同，也不等同于控制台的 CPU 错误计数。
- 09:00 至 13:00 的连续五次 SNAPI 运行均未闭合；最终公开 health 的未闭合日志从 9 条升到 10 条。最新成功完成的来源时间停在 08:02:04，最新文章发布时间为 08:49:13。
- 因此网页和 API 仍能展示已有数据，但新闻源覆盖与后续更新已经受损；共享 D1 不会因为 Worker 中断而自动恢复采集。
- 从 11 月 13 日 08:00 开始的 D1 查询窗口里，Launch Library 2 有 23 次失败、0 次成功，原始错误是 HTTP 429。已有的 126 条未来发射记录是数据库中仍可查询的记录，不构成更新成功的证据。
- ESA 来源报 404；SpaceRef 和部分无锡来源报 403。一次本地 LL2 公共请求返回 200，提示生产环境/出口限流需要单独核对；本轮未确定限流的完整上游原因，也未绕过任何访问限制。

## 本地实现

1. 将来源采集改为每分钟轮转一个启用来源，当前 60 个来源一小时覆盖一轮。使用 Cron 的 scheduledTime，延迟送达不会选错来源；未知调度和缺少时间会明确失败，不会意外执行整批。
2. 每 UTC 整点在来源工作前闭合超过两小时的旧日志，避免只能依赖任务正常结束时维护。
3. D1 文章持久化按最多 40 条分块，分别批量写入、解析 ID 和更新关系。保留去重、重复记录关系更新及旧 schema 兼容；80 条记录测试覆盖新旧 schema，正常调用的绑定请求数不超过 10。
4. RSS 达到有效条目上限后停止继续归一化后续条目。HTML 列表上下文只对保留候选计算，块上下文只清洗一次。RSS XML 解析本身仍需处理原始 feed，这些优化不能保证所有大 feed 低于免费 CPU 上限。
5. 公开只读 JSON API 增加 30 秒边缘缓存，完整 URL 保留筛选与分页隔离；health、admin、授权/Cookie 请求、非 JSON、错误、Set-Cookie、private/no-store 响应绕过缓存。缓存故障回落到原处理器。
6. 非首页路由按需加载；React Query 的取消信号传入 fetch；未知地址提供返回首页入口。
7. 健康诊断区分 resource_limit、rate_limited 与普通 HTTP/解析/数据库错误，继续避免发布原始异常详情。
8. 修复 Windows CRLF 引起的配置漂移误报，并让 lint 排除 Wrangler 生成目录。

## 生产验证与后续工作

- 当前修改尚未部署；本报告不宣称线上错误已修复。
- 审查通过后，部署 Pages 与独立 scheduled Worker，并核对旧小时 Cron 被替换。Cron 配置传播期间允许存在过渡。
- 至少观察一个完整来源轮转：逐源完成情况、未闭合日志、CPU 错误、子请求错误和文章来源覆盖。
- 核对 LL2 在 Worker 出口的响应与限流头，等待允许的重试窗口；429 不会因单源拆分而自动消失。优先解决 ESA 的官方 feed 地址与拒绝访问来源的可用性。
- 免费 CPU 限额仍适用于每个单源和每日维护。如果个别解析任务继续被终止，下一轮评估将重解析移至独立免费任务执行环境；不要仅提高并发或增加同调用内重试。
- 本轮没有执行生产写入、数据库迁移、采集重跑、套餐升级，也未变更其他站点。
